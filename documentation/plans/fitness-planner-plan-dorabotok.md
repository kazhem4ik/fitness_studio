# Fitness Planner — план доработок для AI-агента

## Как пользоваться этим документом

Это техническое ТЗ для AI-агента (Antigravity), который будет вносить изменения в существующий проект (FastAPI + SQLite + Vanilla HTML/CSS/JS PWA).

**Перед началом работы агент должен:**
1. Изучить реальную структуру репозитория — названия файлов, роутов, функций могут отличаться от условных имён в этом документе.
2. Проверить, какие из перечисленных backend-эндпоинтов уже существуют, а какие нужно создать с нуля.
3. Не ломать существующую цветовую схему, стили модалок и общий визуальный язык приложения (bottom sheet, кнопки, бейджи) — все новые UI-элементы должны быть в едином стиле.
4. Работать по одной задаче за раз, с возможностью протестировать перед переходом к следующей.

Задачи разбиты на 4 фазы. Рекомендуемый порядок — от фундамента к надстройкам, чтобы не переделывать одно и то же дважды.

---

## Фаза 0 — Фундамент: единый компонент модалки взамен `prompt()`

Делать первой, так как задачи 3.1 (расходы/доходы) и часть задачи 2.3 (абонементы) будут использовать этот же компонент — если сделать его один раз, экономим время на остальных фазах.

### Цель
Убрать нативные `prompt()` при добавлении расхода/дохода/абонемента, заменить на единообразные bottom-sheet модалки в стиле остальных форм приложения (как модалка «Запись» или «Клиент»).

### Что сделать
- Создать переиспользуемый компонент модалки (если такого ещё нет как отдельной сущности) с:
  - заголовком,
  - слотом для полей формы,
  - кнопками «Отмена» / основное действие (цвет зависит от контекста — зелёный для дохода/сохранения, красный для расхода/удаления),
  - валидацией на клиенте (обязательные поля, числовые ограничения),
  - блоком ошибки по аналогии с модалкой записи.
- Модалка должна открываться/закрываться той же анимацией снизу экрана, что и остальные модалки.

### Acceptance criteria
- [ ] Нигде в коде не используется `prompt()` или `confirm()` для ввода данных (только для критичных подтверждений типа удаления, если это уже принятый паттерн — уточнить у пользователя).
- [ ] Компонент модалки переиспользуется минимум в 3 местах (доход, расход, абонемент).

## Фаза 1 — Карточка клиента: история, заметки, не пришёл

### 1.1 История записей клиента

**Цель:** тренер должен видеть в карточке клиента список всех его тренировок, а не только текущий баланс.

**Backend:**
- Endpoint `GET /clients/{id}/appointments` уже существует (по документации проекта) — проверить формат ответа: поля должны включать дату, время, тип тренировки, цену, статус оплаты, `is_attended`, `is_no_show`, `is_cancelled`.
- Если каких-то полей не хватает в ответе — добавить их в сериализацию.
- Добавить сортировку по дате (новые сверху) и пагинацию/лимит (например, последние 50), если её ещё нет.

**Frontend — модалка «Карточка клиента»:**
- Добавить новый блок/вкладку внутри существующей модалки: «История записей» под блоком баланса.
- Список карточек-строк, каждая:
  - дата + время,
  - тип тренировки (цветной бейдж, как в дневном виде),
  - статус: «Оплачено» / «Не оплачено», и отдельно — «Пришёл» / «Не пришёл» / «Отменено» (если применимо).
  - цена.
- Пустое состояние: «Записей пока нет».
- Если записей много — показать первые N с кнопкой «Показать ещё» или скролл внутри блока (не растягивать всю модалку).
- Отменённые записи (`is_cancelled = true`) показывать визуально приглушённо, но не скрывать — тренеру важно видеть паттерн отмен.

**Acceptance criteria:**
- [ ] При открытии карточки клиента подгружается его история (лениво, при открытии модалки, а не сразу при рендере списка клиентов).
- [ ] Данные соответствуют реальным записям в БД, статусы отображаются корректно.
- [ ] Работает при 0 записей и при 50+ записях без поломки вёрстки.

### 1.2 Управление `is_no_show`

**Цель:** тренер может явно отметить, что клиент не пришёл, — сейчас это поле есть в БД, но нигде не выставляется.

**Уточнить перед реализацией:** как соотносятся `is_attended` и `is_no_show` в текущей логике автосписания (см. раздел 3 документации проекта — автоматическое списание при `time_end < now`). Нужно решить: становится ли запись автоматически «не пришёл», если её никто не отметил вручную, или это строго ручное действие тренера. Рекомендация — сделать статус трёхзначным по факту: «не отмечено» → «пришёл» → «не пришёл», где авто-логика по времени только помечает «прошедшая» / не трогает `is_no_show`.

**Backend:**
- Добавить (или проверить наличие) `PATCH /appointments/{id}/attendance` с телом `{ "status": "attended" | "no_show" }`.
- При простановке `no_show = true` — **не** списывать занятие с баланса клиента (если сейчас списание завязано на `is_attended`, логику нужно развести: списание только при реальном посещении).
- При смене статуса с `no_show` на `attended` (если тренер ошибся) — списать занятие; предусмотреть отмену списания при обратном действии, чтобы баланс не «утекал».

**Frontend — карточка записи в дневном виде (apt-card):**
- Добавить два маленьких тоггла/кнопки в карточке прошедшей записи: «✓ Пришёл» / «✗ Не пришёл» (показывать только для записей, время которых уже прошло, и не показывать для отменённых).
- Текущий выбранный статус — подсвечен.
- Изменение статуса — мгновенное (без отдельного сохранения), с оптимистичным обновлением UI.

**Acceptance criteria:**
- [ ] Тренер может отметить/изменить статус посещения из дневного вида без открытия модалки редактирования.
- [ ] Баланс занятий клиента корректно меняется только при статусе «Пришёл», без двойного списания.
- [ ] Статус отражается в истории записей клиента (задача 1.1).

### 1.3 Заметки о клиенте (`notes`)

**Цель:** дать тренеру возможность фиксировать травмы/ограничения/договорённости по клиенту — поле в БД уже есть.

**Backend:**
- Проверить, что `notes` возвращается и принимается в существующих endpoint'ах создания/редактирования клиента (`POST/PUT /clients`). Если нет — добавить в сериализацию запроса/ответа.

**Frontend:**
- Добавить `textarea` «Заметки» в модалку «Новый/Редактировать клиент» (после поля «Телефон»).
- В модалке «Карточка клиента» (просмотр) — отображать заметки, если они есть, отдельным блоком под телефоном (не показывать пустой блок, если заметок нет).

**Acceptance criteria:**
- [ ] Заметка сохраняется и подгружается при повторном открытии карточки клиента.
- [ ] Пустое поле не ломает отображение (не показываем «null» или пустой блок).

## Фаза 2 — Финансы

### 2.1 Редактирование и удаление расходов/доходов

**Цель:** `PUT`/`DELETE` endpoints уже есть на бэкенде — довести до UI, чтобы можно было исправить ошибку без компенсирующей записи.

**Backend:**
- Проверить существующие `PUT /expenses/{id}`, `DELETE /expenses/{id}`, `PUT /incomes/{id}`, `DELETE /incomes/{id}` — убедиться, что они принимают/возвращают все нужные поля (сумма, категория, комментарий, дата).

**Frontend — вкладка «Финансы», список «Последние операции»:**
- По клику/тапу на строку операции — открывается модалка редактирования (использовать компонент из Фазы 0) с предзаполненными полями: сумма, категория (select), комментарий, дата.
- В модалке — кнопка «Сохранить» и кнопка «Удалить» (с подтверждением — простой `confirm()` тут допустим, либо мини-диалог подтверждения в том же стиле).
- **Важно:** операции, пришедшие из записей клиентов («Клиент: Имя»), в этом списке — это доход, связанный с оплатой тренировки, а не отдельная финансовая запись. Разграничить:
  - если строка — ручной доход/расход (`incomes`/`expenses`) → открывается редактирование;
  - если строка — доход от оплаты записи (привязан к `appointments`) → редактирование этой суммы должно вести в модалку редактирования самой записи (или быть недоступно для прямого редактирования из списка финансов, чтобы не рассинхронизировать статус оплаты записи и сумму в финансах).
- После сохранения/удаления — список и карточки-сводки (Доходы/Расходы/Прибыль) должны пересчитываться сразу, без перезагрузки страницы.

**Acceptance criteria:**
- [ ] Ручные доходы/расходы можно отредактировать и удалить прямо из списка операций.
- [ ] Суммы в карточках-сводках и в CSV-экспорте пересчитываются корректно после правок.
- [ ] Доходы, привязанные к записям клиентов, не создают путаницы — либо явно ведут к записи, либо помечены как нередактируемые напрямую здесь.

### 2.2 Разбивка по категориям (`by_category`) и месячный график (`monthly_chart`)

**Цель:** данные уже отдаёт API `/finances/summary`, нужно визуализировать.

**Frontend — вкладка «Финансы»:**
- Под тремя карточками-сводками добавить блок «По категориям» — горизонтальные бары или простой список: категория расхода → сумма → % от общих расходов. Использовать существующие цвета категорий, если они заданы, либо ввести единую палитру для категорий расходов.
- Добавить блок/переключатель «Динамика по месяцам» — простой линейный или столбчатый график (доход/расход/прибыль по месяцам за последние 6–12 месяцев). Можно использовать лёгкую библиотеку графиков или простую SVG-отрисовку, если проект не хочет тянуть зависимости — уточнить у пользователя предпочтение (нужно ли добавлять новую зависимость типа Chart.js, или делать самописный SVG).
- Оба блока должны переключаться синхронно с текущим фильтром периода (Месяц/Неделя/День), либо работать независимо от него — уточнить у пользователя, что логичнее (вероятно, `monthly_chart` логично показывать всегда за последние N месяцев независимо от фильтра, а `by_category` — привязан к выбранному периоду).

**Acceptance criteria:**
- [ ] Разбивка по категориям отображает реальные суммы за выбранный период и корректно обновляется при смене периода.
- [ ] График по месяцам рендерится без сторонних сетевых запросов (или с учётом сетевых ограничений окружения).
- [ ] Блоки корректно показывают пустое состояние, если данных недостаточно (например, меньше 2 месяцев истории).

## Фаза 3 — Консолидация продажи абонемента

**Цель:** убрать дублирование логики между продажей пакета через форму записи и через карточку клиента.

**Рекомендуемое решение:** оставить основной сценарий — «+ Добавить» в карточке клиента (уже описан в документации проекта), с заменой `prompt()` на модалку из Фазы 0 (поля: количество занятий, сумма оплаты, способ оплаты — по аналогии с формой записи). В форме создания записи — убрать поле «Количество занятий» либо явно переименовать его в контекст «разовая продажа абонемента вместе с записью» и оставить только если пользователь подтвердит, что этот сценарий (продать пакет прямо в момент первой записи) реально нужен.

**Перед реализацией — уточнить у пользователя:**
1. Нужен ли вообще сценарий «продать абонемент прямо при создании записи» (например, для первого визита нового клиента), или это можно полностью убрать из формы записи.
2. Если нужен — оставить оба пути, но привести к одинаковой валидации и одинаковому набору полей (сумма, способ оплаты), чтобы не было расхождений в логике пополнения баланса.

**Backend:**
- Убедиться, что оба пути (если оба остаются) вызывают одну и ту же внутреннюю функцию/сервис пополнения баланса и создания записи в `packages`, а не дублируют логику в двух разных обработчиках. Если сейчас это два независимых куска кода — отрефакторить в общую функцию `sell_package(client_id, sessions_count, amount_paid, payment_method)`.

**Frontend:**
- Модалка «+ Добавить» в карточке клиента — заменить `prompt()`-цепочку на единую модалку (количество занятий, сумма, способ оплаты — select, как в форме записи, а не текст).
- Если решено убрать поле из формы записи — убрать соответствующий UI-код и связанный запрос.

**Acceptance criteria:**
- [ ] Единая точка входа для продажи абонемента (или два явно разведённых по смыслу сценария с одинаковой валидацией).
- [ ] Пополнение баланса происходит через общую переиспользуемую логику на бэкенде.
- [ ] Нет расхождений в том, какие способы оплаты доступны в разных местах приложения.

## Общие технические заметки для агента

- **Стиль:** все новые модалки/блоки должны визуально соответствовать существующим (шрифты, отступы, цвета бейджей типов тренировок — см. таблицу цветов в документации проекта, скругления, анимация bottom sheet).
- **Оптимистичные обновления:** там, где это уместно (статус посещения, редактирование финансов), обновлять UI сразу, откатывая при ошибке запроса.
- **Не трогать без необходимости:** логику публичной страницы `/book.html`, JWT-аутентификацию, push-уведомления — эти задачи их не касаются.
- **Тестирование после каждой фазы:** прежде чем переходить к следующей фазе, агент должен убедиться, что:
  - существующий функционал (создание/редактирование записей, календарь, вход) не сломан;
  - новые данные корректно сохраняются в SQLite и переживают перезагрузку страницы.
- **Миграции БД:** если структура таблиц не меняется (поля `notes`, `is_no_show` и т.д. уже существуют по документации проекта) — миграции не нужны, только доработка сериализации в API и UI. Если в реальном коде окажется, что каких-то полей физически нет в таблице — потребуется миграция SQLite (добавление колонки через `ALTER TABLE`), об этом агент должен сообщить отдельно перед продолжением.
